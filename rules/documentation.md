# 文档与绘图规则

编写、扩写或整理本项目文档及说明文字，或绘制说明图时读取。只补充文档规则时，不因此开始研究或绘图。

## 按主题分层，每篇保持简短

- 文档按主题、阶段和子问题组织目录。一个主题需要多篇文档时，放入 `docs/<主题>/`；规则按类别放入 `rules/`。不要为了形式给一篇短文套多层空目录。
- 每篇只回答一个主要问题，篇幅必须简短；严禁把所有内容塞入一篇文档。出现可独立查阅的子主题、长表格或详细推导时，必须先拆分，再继续扩写，不能只靠增加小标题让单篇不断变长。
- 上层文档只保留概述、必要关系和子文档链接，详细内容放到对应子文档。不要在索引、交接和专题文档中各维护一份全文。
- 拆分时保留事实、引用、固定提交和不确定性，修正相关链接与锚点；不要借目录调整改写研究结论。

## 框架与逻辑优先用图解释，先选 ASCII

- 解释团队结构、职责关系、调用或数据流、时序、分支和状态变化时，优先用图辅助理解，再用文字说明图中省略的条件。简单事实或短清单不必硬画图。
- 优先使用 ASCII 图，放在 `text` 代码块中，以等宽方式显示。构图使用 `+`、`-`、`|`、`>` 等 ASCII 字符，使用空格而不是 Tab。
- 绘制或修改后，必须在等宽显示下逐行检查边框、列宽、缩进、连线和箭头落点，确保对齐、美观且含义清楚。中文标签要按显示宽度检查，不能只数字符；必要时缩短标签，在图外补充解释。
- 先考虑按问题拆成几张小图。只有判断 ASCII 即使合理拆分，仍因交叉连线、多维关系或复杂布局而难以清楚表达时，才说明原因，并读取本仓库的 `.agents/skills/diagram-design/SKILL.md`，使用 diagram-design。只需 ASCII 时，不提前加载该技能。
- 图只能表达已核实的信息或明确标注的待核对假设；不能为了画得完整而补造角色、流程或状态。

## 文字直白易懂，拿不准就用 plain-docs

- 尽量写清谁做什么、输入是什么、结果是什么、什么条件下继续或停止。少堆抽象名词、套话和不必要的缩写；必要术语首次出现时解释。
- 拿不准表述是否容易理解，或整理后仍觉得费解时，读取本仓库的 `.agents/skills/plain-docs/SKILL.md`，使用 plain-docs 润色；不要求为每句普通说明都加载技能。
- 润色不得改变事实、决定、责任、限制条件和不确定性。代码标识、命令、路径、正式名称、原文引语与引用保持准确，不改写历史原始证据。
